# Développement

Lancer le projet, le tester, son organisation et son API. Retour au [ReadMe](../ReadMe.md).

## Stack

| Partie | Choix |
| --- | --- |
| Frontend | Angular 22 |
| Backend | Spring Boot 4, Java 25 LTS, Maven |
| Base de données | PostgreSQL 18 |
| Migrations | Flyway Community (gratuit, open source) |
| Auth | Google (OIDC) via Spring Security, session serveur (cookie HttpOnly) |
| Images | Protocole S3 via AWS SDK v2 (BOM). SeaweedFS (compatible S3) en local et sur Coolify : seul l'endpoint change. Identifiants S3 en variables d'environnement, métadonnées des images en base |
| DevOps | Docker Compose sur Coolify : PostgreSQL 18 et SeaweedFS en conteneurs |
| Validation API | ProblemDetail (RFC 9457) |
| Mapping | MapStruct avec une configuration partagée `@MapperConfig` |
| Boilerplate | Lombok limité (getters et setters des entités, constructeur des services), DTO en records |
| Documentation API | springdoc-openapi exposé par le backend, consommé par le front pour générer ses services |
| Hébergement | Serveur perso sur Coolify, Cloudflare en DNS et proxy |

## Structure

```
back/      API Spring Boot
front/     application Angular
devops/    Docker Compose (local : compose.yaml, Coolify : compose.prod.yaml), passerelle Caddy, configuration d'environnement
e2e/       parcours dans Chrome contre le site lancé en local, captures d'écran du ReadMe
docs/      documentation : fonctionnalités, développement, production, architecture, roadmap, restauration, services Google, changement de domaine, remplissage par IA ; captures/ (images du ReadMe)
ReadMe.md, CHANGELOG.md (aussi affiché dans le back-office, « Nouveautés »), LICENSE
```

## Écrire un texte du site

Pas de point à la fin d'un texte affiché (paragraphe, aide, message, confirmation, erreur de l'API, description pour Google) ; les points entre deux phrases restent. Sauf les mentions légales, les conditions d'utilisation et la politique de confidentialité. Détail : [architecture](architecture.md#général).

## Monter la version

Chaque série de changements a sa version, front et backend toujours ensemble (même numéro), en version sémantique `majeure.mineure.correctif` :

| Changement | Version | Exemples |
| --- | --- | --- |
| Casse l'existant (anciennes données, liens ou sauvegardes plus lisibles) | majeure : 1.10.0 → 2.0.0 | |
| Nouvelle fonctionnalité, même petite | mineure : 1.5.3 → 1.6.0 | nombre de vues, sélection multiple dans la corbeille |
| Tout le reste | correctif : 1.5.2 → 1.5.3 | bug, texte ou ponctuation, position dans la page, documentation |

- Une version déjà commitée ne se réutilise pas : le changement suivant prend le numéro d'après. Tant qu'elle n'est pas commitée, ce qui s'ajoute la rejoint (et peut la faire passer de correctif à mineure).
- Une série qui mêle fonctionnalité et correctifs prend le plus fort : mineure.
- Les versions ont été renumérotées en 1.10.0 : la majeure 3 était une erreur, toutes les versions 3.x.y sont devenues 1.x.y (CHANGELOG, documentation). Les sauvegardes déjà faites gardent dans leur manifeste la version d'alors (3.x ou 2.1.0).

À mettre à jour à chaque version :

1. `front/package.json` et `package-lock.json` : `npm version x.y.z --no-git-tag-version` dans `front/`.
2. `back/pom.xml` : la balise `<version>` du projet, à la main.
3. [CHANGELOG.md](../CHANGELOG.md), **en français** (depuis la 2.5.1 ; en anglais de la 1.10 à la 2.5.0, tout réécrit en français), synthétique, en points courts, sans point final (il s'affiche dans « Nouveautés ») : une section `## x.y.z - AAAA-MM-JJ` en haut, puis « Front et backend x.y.z » et la migration (« Migration de la base : V15 » ou « Pas de migration de la base »), puis les rubriques utiles : `### Ajouté`, `### Modifié`, `### Corrigé`, `### Retiré`, `### Technique` (les pastilles de « Nouveautés » en viennent ; un point « **Titre** : détail » montre son titre en gras). Les liens vers un fichier du dépôt en adresse GitHub complète (`https://github.com/ImMaxence/les-creations-de-yona/blob/main/…`) : le CHANGELOG s'affiche aussi dans le back-office (« Nouveautés »), où un lien relatif mènerait à une page du site (la page les convertit quand même, par sécurité).
4. [ReadMe.md](../ReadMe.md) : la ligne « Version x.y.z ».
5. [docs/roadmap.md](roadmap.md) : une ligne `- [x] x.y.z : …` en tête des versions, et les points à vérifier une fois en ligne s'il y en a.
6. La documentation touchée par le changement : [fonctionnalités](fonctionnalites.md), [architecture](architecture.md) (dont le nombre de tests), l'API plus bas dans cette page.
7. `e2e/captures.mjs` : la version passée à `fakeAdmin`, affichée sur la capture du back-office.

Mise en production et affichage des versions : [production.md](production.md).

## Démarrage local

Prérequis : Docker Desktop (Compose v2).

```bash
cd devops
cp .env.example .env   # puis remplacer chaque valeur "change-me"
docker compose up -d --wait
```

| Service | Image | Accès depuis la machine |
| --- | --- | --- |
| PostgreSQL | `postgres:18.6-alpine` | `localhost:5432` |
| SeaweedFS (API S3) | `chrislusf/seaweedfs:4.48` (`weed mini`) | `http://localhost:8333` |
| Backend (profil `app`, facultatif) | construit depuis `back/Dockerfile` | `http://localhost:8080` |
| Front SSR (profil `app`) | construit depuis `front/Dockerfile` | via la passerelle uniquement |
| Passerelle (profil `app`) | construite depuis `devops/gateway/` (Caddy 2.11.7) | `http://localhost:8000` : application complète |

- Ports exposés sur `127.0.0.1` uniquement, jamais sur le réseau local.
- Base créée avec la collation ICU `fr-FR` (tri français des titres). Checksums de données activés (défaut de PostgreSQL 18).
- Bucket `S3_BUCKET` créé au démarrage, privé : accès anonyme refusé, seuls les identifiants `S3_ACCESS_KEY` / `S3_SECRET_KEY` y accèdent. Pas de création automatique d'autres buckets, suppression d'un bucket non vide refusée. Télémétrie SeaweedFS désactivée.
- Arrêt : `docker compose down`. Remise à zéro complète (supprime les données) : `docker compose down --volumes`.
- Journaux : 3 fichiers de 10 Mo au plus par conteneur (`x-logging`), effacés aussi quand le conteneur est recréé (chaque déploiement). Cohérent avec la politique de confidentialité (12 mois au plus).
- Application complète dans Docker, sans JDK ni Node sur la machine : `docker compose --profile app up -d --build --wait`, puis `http://localhost:8000`. La passerelle (`devops/gateway/Caddyfile`, intégré à son image) envoie `/api/*` au backend et le reste au front, en local comme en production. Arrêt : `docker compose --profile app down`.

### Backend

Prérequis : JDK 25. Les services Docker Compose doivent tourner.

```bash
cd back
./mvnw spring-boot:run   # Windows : .\mvnw.cmd spring-boot:run
./mvnw test              # tests unitaires (sans base ni Docker)
```

- Tests unitaires sans JDK sur la machine : `docker run --rm -v "$PWD:/build" -v yona-m2:/root/.m2 -w /build eclipse-temurin:25.0.4.1_1-jdk-resolute ./mvnw --batch-mode test` depuis `back/` (sous Git Bash, préfixer par `MSYS_NO_PATHCONV=1` et utiliser `$(pwd -W)`).

- Lit les identifiants de `devops/.env` (lancement depuis `back/`). En production, mêmes clés en variables d'environnement, plus `POSTGRES_HOST` et `S3_ENDPOINT` (par défaut `http://localhost:8333`).
- Flyway applique les migrations de `back/src/main/resources/db/migration` au démarrage. Hibernate vérifie seulement que les entités correspondent au schéma (`ddl-auto: validate`).
- Santé : `http://localhost:8080/actuator/health`.
- Documentation de l'API : `http://localhost:8080/api/docs` (OpenAPI, lu par le front pour générer ses services) et `http://localhost:8080/api/docs/ui` (Swagger UI). Désactivée par défaut, activée en local par `API_DOCS_ENABLED=true` dans `devops/.env`. En production, la variable reste absente : les URL de documentation sont refusées comme toute route inconnue.
- Connexion admin : client OAuth Google à créer (type « Application Web »), avec les URL de retour listées dans `devops/.env.example`. Renseigner `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` et `APP_ADMIN_EMAILS` dans `devops/.env`. Application Google laissée en mode « Test », avec les adresses admin dans « Utilisateurs test ».
- Sauvegarde : nécessite le client `pg_dump` 18. Il est inclus dans l'image Docker. En lancement local, l'installer et renseigner `PG_DUMP_PATH`, sinon la route répond 503 `BACKUP_UNAVAILABLE`.
- Encodage WebP : libwebp est une bibliothèque native, autorisée par `--enable-native-access=ALL-UNNAMED` (déjà passé par `spring-boot:run` et par l'image Docker).

Image Docker (`back/Dockerfile`) : build Maven multi-étapes, jar découpé en couches Spring Boot, JRE Temurin 25 sur Ubuntu 26.04 avec `postgresql-client-18`, utilisateur non root, health check sur `/actuator/health`.

Cache des réponses publiques (1.14, `common/PublicCache`, Spring Cache et Caffeine) : les recettes, la recette à la une, les recettes proches, les suggestions de recherche, les catégories, menus, tags, glossaire, ingrédients, rayons, réseaux sociaux, textes du site et apparence sont gardés en mémoire, 500 réponses par cache et 10 minutes au plus. Tout est oublié d'un coup après une écriture du back-office (`PublicCacheEviction` sur `/api/admin/**`, sauf GET), une publication programmée ou une restauration de sauvegarde : jamais plus ancien que le dernier changement. Mesuré en local : environ 10 ms par réponse au lieu de 15 à 50 ms, une page rendue par le serveur en 80 à 100 ms au lieu de 110 à 200 ms. Quelques Mo de mémoire.

Mémoire du backend : réglages par défaut de la JVM, de Hikari et de Tomcat depuis la 2.6.1, sauf le tas Java, limité à 512 Mo (`-Xmx512m` dans `back/Dockerfile` ; sans lui, le quart de la mémoire de la machine, gardé une fois pris). Les deux compilateurs (C1 puis C2, plus rapide à plein régime) ; G1 et les threads du compilateur, un par cœur ; 10 connexions à la base (Hikari, le pool de connexions de Spring Boot : une connexion n'est prise que le temps d'une requête SQL, quelques millisecondes, 10 servent donc bien plus de 10 visiteurs à la fois ; au-delà, la requête attend son tour), 200 threads Tomcat au plus. Mesuré en local (16 cœurs, 16 Go) après quelques centaines de pages : environ 890 Mo pour tout le processus avec le tas à 512 Mo (1 Go sans limite du tas, 300 Mo avec les limites d'avant). Le tas n'est qu'une partie : s'y ajoutent les classes chargées, le code compilé par C1 et C2, et la pile de chaque thread (plus nombreux avec plus de cœurs).

Les limites des 1.12 et 1.13, retirées en 2.6.1 (environ 370 à 400 Mo au repos, au lieu de 700 à 800 Mo avant) : tas de 256 Mo au plus (512 Mo depuis), G1 avec une collection par minute au repos qui rendait la mémoire libre (`G1PeriodicGCInterval`, `Min/MaxHeapFreeRatio`), threads du ramasse-miettes et du compilateur réglés pour 2 cœurs, compilateur rapide seul (C1, `TieredStopAtLevel=1`), mémoire native rendue chaque minute (`TrimNativeHeapInterval`), 2 zones malloc (`MALLOC_ARENA_MAX`), en-têtes d'objets compacts (Java 25), 5 connexions à la base et 40 threads Tomcat. Restées, car elles accélèrent sans rien limiter : le chargement groupé des associations (`hibernate.default_batch_fetch_size`) et le cache des réponses publiques.

Pour mesurer : la mémoire du backend dans Statistiques, ou `-XX:NativeMemoryTracking=summary` puis `jcmd 1 VM.native_memory summary` dans un conteneur JDK.

### Frontend

Prérequis : Node.js 24 LTS. Le backend doit tourner (`http://localhost:8080`, en local ou dans Docker).

```bash
cd front
npm ci
npm start              # http://localhost:4200, avec SSR, /api relayé vers le backend (proxy.conf.json)
npm run build          # build de production (navigateur + serveur SSR) dans dist/
npm test               # tests unitaires (Vitest, dans Node.js avec jsdom), sans backend
npm run api:generate   # régénère le client API depuis http://localhost:8080/api/docs
npm run fonts:generate # régénère src/styles/_fonts.scss après une mise à jour d'un paquet @fontsource-variable
```

- Client API généré par `ng-openapi-gen` dans `src/app/core/api/generated` (versionné, ne pas modifier à la main). À régénérer après chaque changement d'API du backend.
- Budgets de build (`angular.json`) : bundle initial 800 Ko (avertissement), styles d'un composant 8 Ko.
- Icônes : composant maison `<svg yonaIcon="heart" [size]="18">` (`shared/ui/icon/`), dessiné en SVG inline depuis `icons.ts`, qui ne contient que les icônes utilisées (tracés Lucide, licence ISC). Remplace `@lucide/angular` (1.1.0) : bundle initial ramené de 730 à 505 Ko de JavaScript brut (`main` de 448 à 223 Ko), nouvelles fonctionnalités comprises, soit moins de code à analyser au premier chargement sur téléphone ; le poids transféré, déjà bien compressé, change peu (135 → 133 Ko). Ajouter une icône : copier ses formes depuis lucide.dev dans `icons.ts`, sous son nom.
- Choix en pilule (2.7.4) : `yonaSegmented` sur la rangée (`shared/ui/segmented/`, styles dans `styles/_segmented.scss`) ; le choix est lu sur ses options (`aria-pressed`, `aria-checked`, `aria-selected` ou `.is-chosen`), une pastille glisse dessous. Accent par défaut ; pastille blanche surélevée : `--segmented-thumb: var(--color-bg)` et `--segmented-thumb-shadow: var(--shadow-sm)` sur la rangée.
- Liste flottante (2.8) : `yonaFloating` (`shared/ui/floating/`) sur la liste d'un select ou de suggestions, `[yonaFloating]="champ"` ; elle passe dans la couche du dessus du navigateur (popover manuel), placée sous le champ (au-dessus s'il y a plus de place), suit le défilement : aucune fenêtre ni aucun encart ne la coupe.
- Back-office, composants partagés (2.8) : `yona-editor-bar` (barre du bas d'un éditeur : retour, aperçu, brouillon ou publier ; `submits` pour un formulaire), `yona-preview-frame` (Ordinateur ou Téléphone autour d'un aperçu ; la page doit se mettre en page avec des container queries), `yona-publication-status` (Brouillon, Programmé·e, Publié·e, Échec, `feminine` pour une recette), `yona-title-search` (un élément trouvé par son titre, sous `yona-recipe-search` et `yona-article-search`). Styles d'une publication (échec, programmation) dans `admin-publication.scss`.
- Messages (2.8) : `pages/admin/messages/` ; une mention est écrite dans le texte, `@[nom](GENRE:id)` (`message-format.ts` : lecture, liens, adresses web, insertion depuis le champ qui montre « @nom ») ; le champ et ce qui l'entoure dans `message-composer` (photos envoyées dès qu'elles sont choisies, aperçu du premier lien, « est en train d'écrire »), un groupe dans `group-dialog`. Backend `fr.lescreationsdeyona.message` (`AdminMessages` et `AdminGroups` en JdbcClient, `Mentions` qui lit les noms et les trie en mémoire, `LinkPreviews` : `LinkFetcher` lit la page sur une adresse publique seulement, `LinkPages` ses balises Open Graph). Tables `admin_message`, `admin_group`, `admin_group_member` et `admin_message_image`, fusionnées à la restauration (`RestoredData.mergeMessages` et `mergeGroups`) ; `admin_group_seen` (ce que chacun a lu de chaque groupe) reste au serveur. Photos : images de type `MESSAGE` (dossier `messages/`), hors galerie et refusées par `/api/images`.
- Éditeurs (2.9) : `EditHistory` (`pages/admin/edit-history/`) donne Ctrl+Z et Ctrl+Y à un éditeur : il reçoit l'état entier après chaque changement (`record(état, sujet)`, dans un `effect`), regroupe les mots tapés (événements `input` de l'hôte) et remet un état d'avant (`write`) ; `replace` après un enregistrement, un autre sujet (une autre recette) repart de zéro ; `(document:keydown)` et `(input)` sur l'hôte, `[history]` sur `yona-editor-bar`, `data-own-undo` sur un champ hors de l'état. `yona-markdown-tools` (`pages/admin/markdown-tools/`) : les boutons d'un champ Markdown et leurs touches ; `markdown-edit.ts` lit les styles d'une ligne comme CommonMark (paires de `*`, règle de 3) avant de les réécrire, et change le texte comme une frappe (événement `input`).
- Temps réel (2.8) : `AdminLive` (`pages/admin/layout/admin-live.ts`) tient le WebSocket `/api/admin/live` ; `inject(AdminLive).on('TRASH', () => …)` dans un constructeur, oublié avec le composant. Côté backend, publier `new LiveChange(LiveTopic.X)` là où ça change (après le commit), ou `new LiveChange(LiveTopic.X, emails)` pour certains admins seulement (les membres d'un groupe) ; `AuditLog` le fait déjà pour Historique, Corbeille, Commandes et Retours. « est en train d'écrire » (2.9) : `live.typing(groupe)` (par HTTP quand le WebSocket est coupé, 2.10.0) et `live.onTyping(…)`, sans regroupement ; sans WebSocket (`live.connected()` faux), les écouteurs de `MESSAGES` sont appelés toutes les 4 secondes et tous les autres toutes les 32 secondes, comme si quelque chose avait changé, et trois échecs sans jamais se connecter sont envoyés une fois dans « Journaux » (`LiveUnreachable`), la page cachée seulement les messages, toutes les 16 secondes ; le son des messages (`messages/message-sound.ts`, Web Audio) joue quand le badge de « Messages » grandit (`AdminWatch`) ou qu'un message arrive dans la conversation ouverte ; le backend lit l'admin de chaque connexion (son compte Google) et demande les membres à `TypingAudience` (`AdminGroups`).
- Liste longue : pas de pagination (2.1). `new InfiniteList({ load, key, params })` dans un champ du composant (`first` si un resolver a déjà la première page), `<yona-infinite-scroll [list]="liste" />` après la liste (`linked` pour un vrai lien `?page=n` sur les pages publiques). Grille de photos : `yonaVirtualItem` sur chaque élément et `@if (item.near())` autour de son contenu. Liste de texte du back-office : classe `admin-list--infinite`.
- Ajouter une police : paquet `@fontsource-variable/…` (version exacte), ligne dans `scripts/generate-fonts.mjs`, `npm run fonts:generate`, entrée dans `core/theme/theme-fonts.ts`, enum et contrainte CHECK côté backend (migration), crédits des mentions légales.
- Serveur SSR de production : `npm run serve:ssr` (port `PORT`, 4000 par défaut). Variables :
  - `API_URL` : URL interne du backend (ex. `http://back:8080`). Le serveur SSR l'appelle directement, sans repasser par Cloudflare. Sans elle, il appelle l'origine publique du site.
  - `NG_ALLOWED_HOSTS` : hôtes acceptés en plus de `les-creations-de-yona.fr` (protection SSRF d'Angular), ex. `localhost` pour un test local.
  - `NG_TRUST_PROXY_HEADERS` : en-têtes du proxy à prendre en compte (`x-forwarded-host,x-forwarded-proto,x-forwarded-for`), seulement si le serveur n'est joignable qu'à travers ce proxy.
- Cache HTTP : pages rendues par le serveur `private, no-cache` (1.7 : gardées par aucun proxy, revérifiées à chaque fois) ; fichiers hashés (JS, CSS, polices) un an `immutable` ; fichiers de `public/` (favicon, photo de l'auteur) un jour, car leur nom ne change pas, sauf `robots.txt` une heure (1.18 : Cloudflare le garde aussi, il servait l'ancien un jour durant) ; fichiers du service worker (`ngsw.json`, `ngsw-worker.js`, manifeste) jamais en cache, pour que les applications installées reçoivent les mises à jour.
- En-têtes de sécurité (`src/server/security-headers.ts`), posés par le serveur de production sur toutes ses réponses (pas par `npm start`, dont les scripts seraient bloqués) :
  - CSP : scripts du site uniquement. Les scripts inline du build (contrat d'event replay) sont autorisés par leur hash, calculé au démarrage depuis les fichiers HTML construits ; celui qu'Angular écrit au rendu par un nonce aléatoire propre à chaque réponse (`REQUEST_CONTEXT`, puis `CSP_NONCE`). Styles inline autorisés (styles de composants Angular). Aucune intégration dans une iframe (`frame-ancestors 'none'`). Iframes limitées au lecteur YouTube `youtube-nocookie.com` (vidéos des recettes, chargées au clic).
  - Inlining du CSS critique désactivé (`angular.json`) : son script de chargement ne peut pas recevoir le nonce. Coût faible, la feuille de style globale fait environ 15 Ko (2,5 Ko compressée).
  - HSTS (un an, sans sous-domaines), `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy` (caméra, géolocalisation, paiement coupés ; micro pour le site lui-même seulement, pour « Dicter » ; le maintien de l'écran allumé reste permis), `Cross-Origin-Opener-Policy`. `X-Powered-By` retiré.
- Référencement :
  - `/sitemap.xml` (`src/server/sitemap.ts`) : construit à chaque demande depuis l'API (accueil, recettes, catégories ayant au moins une recette, toutes les recettes publiées, « À propos », installation, glossaire s'il a des mots, pages légales), en cache une heure. URL sur le domaine de production.
  - `public/robots.txt` : tous les robots permis (1.18), API exclue sauf les photos, lien vers le sitemap. `/admin` n'y figure pas exprès : ses pages répondent `X-Robots-Tag: noindex, nofollow`, que les robots doivent pouvoir lire. Les robots des assistants et des IA sont nommés dans le même groupe que `*`, mêmes règles : ceux qui répondent avec un lien (OAI-SearchBot, ChatGPT-User, PerplexityBot, Claude-SearchBot…) et, depuis la 1.18, ceux qui collectent pour l'entraînement des modèles (GPTBot, ClaudeBot, CCBot, Applebot-Extended, Meta-ExternalAgent…), refusés en 1.16 et 1.17. Les [conditions d'utilisation](../front/src/app/pages/legal/terms-of-use.html) le disent aussi (fouille de textes et de données, article L122-5-3 du CPI) : à changer ensemble.
  - `/llms.txt` (`src/server/llms.ts`, 1.16, [llmstxt.org](https://llmstxt.org)) : le site décrit pour les assistants IA (texte « À propos », recettes salées puis sucrées avec leurs catégories, menus, pages), construit à chaque demande depuis l'API, en cache une heure. `/llms-full.txt` (1.18) : tout le texte en un fichier, les pages en Markdown l'une après l'autre (« À propos », chaque recette en entier, salées puis sucrées, chaque menu, le glossaire), recettes lues 5 par 5 sur l'API, en cache une heure.
  - Pages en Markdown (`src/server/markdown.ts`, recettes depuis la 1.16, toutes les pages indexables depuis la 1.18) : le contenu de la page sans le site autour (navigation, filtres, boutons). Deux façons de le demander : l'adresse de la page + `.md` (`markdownPathOf` : `/index.md` pour l'accueil, `/recettes.md?categorie=desserts` ; `/a-propos/index.md` et `/index.html.md` répondent aussi), ou l'adresse de la page elle-même avec `Accept: text/markdown` (les navigateurs, qui demandent `text/html` ou `*/*`, reçoivent la page). Réponse `Vary: Accept` ; à l'adresse de la page, `private, no-cache` comme le HTML (Cloudflare ignore `Vary`), une heure pour les `.md`. En-tête `Link: rel="canonical"` vers la page, annoncé par chaque page indexable (`markdownPath`, `<link rel="alternate" type="text/markdown">`, retiré des pages `noindex`).
    - Écrites depuis l'API (`page-markdown.ts`, `recipe-markdown.ts`) : accueil, recettes et catégories (une recherche ou un autre filtre n'a pas de version Markdown), recettes, menus, glossaire, « À propos ». Un brouillon, une recette, un menu ou une catégorie inconnus donnent la page 404 ; une recette sous une autre catégorie, une redirection 301.
    - Converties depuis la page rendue par le serveur (`rendered-markdown.ts`, Turndown) : installation et pages légales, dont le texte est dans le template. Le contenu de `<main>`, sans boutons, champs, icônes, images, éléments masqués ni surtitre (`.eyebrow`) ; chaque onglet (`role="tabpanel"`) sous son nom. Une nouvelle page de ce genre s'ajoute à `RENDERED_PAGES`, avec `markdownPath` dans sa route.
  - Appels à l'API de ces fichiers : `src/server/api.ts` (`API_URL`, comme le rendu SSR).
  - Texte lisible sans JavaScript (1.18) : tout le texte d'une page publique est dans le HTML rendu par le serveur, sans attribut `hidden` (vérifié avec [Readability](https://github.com/mozilla/readability), l'extracteur du mode lecture de Firefox). Les onglets de la page d'installation sont tous dans le HTML, les autres cachés par une classe. Readability extrait en entier les recettes, les pages légales, l'installation, le glossaire et l'accueil ; des pages de liste (recettes, catégories, menus), il garde peu, leurs cartes étant des liens (écartés par principe) : leur version Markdown les donne en entier.
  - Image des cartes de partage (`og:image`) : la photo de la page (recette, catégorie, menu, Yona), sinon l'icône du site (`DEFAULT_IMAGE`).
  - JSON-LD (`core/seo/json-ld.ts`) : un seul graphe par page, qui commence par le site (`WebSite`, `#site`) ; Yona (`Person`, `/a-propos#yona`) auteur de chaque recette, décrite en entier sur l'accueil et « À propos ».
  - Visites venant des assistants IA (`core/analytics/ai-visits.ts`, 1.16) : au premier chargement d'un onglet, l'adresse quittée (`document.referrer`) ou le `utm_source` du lien (ChatGPT ajoute `utm_source=chatgpt.com`) donne l'assistant, envoyé une fois (`POST /api/ai-visits/{assistant}`).
- Notifications (Web Push) : `core/pwa/new-recipe-notifications.ts` (`SwPush` d'Angular, clé publique lue sur `/api/notifications/public-key`), bouton `shared/ui/notify-button`. La notification reçue est affichée par le service worker d'Angular (champ `notification` du message), un appui ouvre la recette (`onActionClick`, `navigateLastFocusedOrOpen`). Sans service worker (`npm start`), le bouton n'apparaît pas. Dans un onglet sans service worker (2.6), il est enregistré au moment de les activer, après l'accord du navigateur demandé sur l'appui même (l'installation du service worker peut prendre quelques secondes, et le navigateur ne pose sa question que juste après un appui) ; même chose pour l'alerte des commandes (`core/pwa/order-alerts.ts`).
- Application installable (PWA) : service worker Angular (`ngsw-config.json`), actif seulement dans le build de production. Depuis la 2.6, enregistré seulement là où il sert (`core/pwa/service-worker-gate.ts`, `registrationStrategy` de `provideServiceWorker`) : l'application installée (ouverte en application, ou installée sur l'appareil : `InstallPrompt.installed`, le navigateur et l'application partageant un seul service worker sur Android et sur ordinateur) et un appareil abonné aux notifications (Web Push en a besoin). Dans un onglet, rien : chaque page vient du serveur (rendu SSR), toujours à la version en ligne, sans « Une nouvelle version du site est prête » après chaque déploiement ; le service worker installé dans un onglet par une version d'avant y est désinscrit, et ses copies (caches `ngsw:…` et `yona-api`, pas `yona-local-ai`) effacées au chargement suivant, une fois qu'il ne sert plus la page (sans elles, il la rechargerait). L'installation n'en dépend pas : Chrome propose l'application sans service worker (`beforeinstallprompt` reçu, aucune erreur dans `Page.getInstallabilityErrors`, Chrome 157). Pour le tester en local : `npm run build`, puis `npm run serve:ssr` ou l'application complète dans Docker. Icônes dans `public/icons/`, manifeste dans `public/manifest.webmanifest`. Nom sous l'icône une fois installée : « Recette Yona » (`short_name` du manifeste, `apple-mobile-web-app-title` pour iOS).
- Les écritures (POST, PUT, DELETE) contournent le service worker (en-tête `ngsw-bypass`) : relayé par lui, Safari sur iOS perd le fichier envoyé lors de l'upload d'une photo.
  - Pages (1.7, `navigationRequestStrategy: performance`) : une fois le service worker installé (application installée, notifications), servies tout de suite depuis l'appareil (`index.csr.html`, rendu dans le navigateur), avec ou sans réseau ; seule la première visite et les robots reçoivent le rendu SSR. Avant la 1.7 (`freshness`), la page était demandée au réseau sans délai maximum, et n'importe quelle réponse servie telle quelle : derrière un proxy d'entreprise ou un Wi-Fi sans Internet, 30 secondes d'attente puis la page « Forbidden » du proxy au lieu de la version hors ligne.
  - API publique (`/api/recipes`, catégories, menus, tags, réseaux sociaux, glossaire…), depuis la 1.14.1 : plus relayée par le service worker, qui la faisait attendre des secondes pendant l'installation d'une nouvelle version. La page l'appelle directement (en-tête `ngsw-bypass`) et en garde une copie dans le cache du navigateur (`core/pwa/api-cache.ts`, cache `yona-api`) ; sans réponse en 3 secondes, sans réseau, ou refusée par un proxy (403, 5xx), la copie est lue. Depuis la 2.6, seulement quand un service worker sert la page : un onglet ne garde rien.
  - Mises à jour (`core/pwa/app-updates.ts`, `SwUpdate`), là où un service worker sert la page : une nouvelle version, téléchargée en arrière-plan, est proposée aussitôt (1.14 : notification « Une nouvelle version du site est prête », bouton « Mettre à jour », qui reste jusqu'à ce qu'on la ferme) et prise de toute façon au changement de page suivant (rechargement complet, après les guards) ; vérifiée aussi au retour de l'application à l'écran et au retour de la connexion ; un cache cassé (`unrecoverable`) recharge la page.
  - Version du backend (1.14) : chaque réponse de `/api` porte `X-App-Version` (`version/VersionHeaderFilter`), lu par `core/pwa/version-check.ts`. Plus récente que le front, la page a été ouverte avant un déploiement : dans un onglet sans service worker, « Mettre à jour » est proposé (un rechargement donne la version du serveur) ; sinon, le service worker cherche la nouvelle version tout de suite (au plus une fois toutes les 30 s, le front étant déployé un peu après le backend), sans attendre le prochain changement de page.
  - Back-office (1.14) : exclu de la navigation du service worker (`navigationUrls` : `!/admin`, `!/admin/**`), il est toujours chargé depuis le serveur, donc à sa version ; la copie des pages publiques suit sans rien dire, sauf si le back-office a été ouvert pendant le déploiement (alors il propose aussi « Mettre à jour » ; le brouillon de la recette est gardé dans le navigateur).
  - Connexion (1.14, `core/pwa/connection-status.ts`) : « Hors connexion : les recettes déjà ouvertes restent lisibles » (« Hors connexion : la page affichée reste lisible » dans un onglet sans service worker, 2.6) tant que l'appareil n'a plus de réseau (événements `offline` et `online` du navigateur ; un Wi-Fi sans Internet n'est pas repéré), puis « Connexion retrouvée ».
  - Application installée vue d'un onglet : `core/pwa/install-prompt.ts`, voir [fonctionnalités](fonctionnalites.md) (« Installer l'application ») ; le manifeste déclare `related_applications` sur le domaine de production.
  - Images : servies depuis le cache (leur URL change à chaque nouvelle photo), 30 jours.
  - `/api/admin/**` et la connexion Google ne passent jamais par le cache.
  - Une page rendue par le serveur reçoit ses données dans le HTML, sans appel à l'API : ces requêtes sont rejouées une fois en arrière-plan après le chargement (`core/pwa/offline-warmup.ts`), pour que la page soit aussi lisible hors connexion.

Image Docker (`front/Dockerfile`) : build Node 24 multi-étapes, image finale sans `node_modules` (le serveur SSR embarque ses dépendances), utilisateur non root, health check sur `/healthz` (répond sans rendu Angular).

Organisation de `front/src` :

```
app/core/      services globaux, layout (header, menus, footer), thème (couleurs, polices, clair/sombre), favoris et liste de courses (kitchen/), client API généré
app/shared/    composants d'interface (bouton, carte de recette, image), directive de reveal, utilitaires
app/pages/     une page par route, chargée à la demande
styles/        variables (espacements, breakpoints, animations), polices (généré), reset, base typographique, animations, impression
server/        middlewares du serveur SSR Express (en-têtes de sécurité, sitemap, llms.txt et llms-full.txt, pages en Markdown) ; point d'entrée : server.ts
scripts/       génération de styles/_fonts.scss (npm run fonts:generate)
```

### Parcours dans Chrome (e2e)

Avant une mise en ligne, le site lancé en local (`docker compose --profile app up -d --build --wait`), dans `e2e/` :

```bash
npm ci
npm test               # 212 vérifications dans Chrome (environ 9 min), captures d'écran dans e2e/resultats/
npm run captures       # refait les images du ReadMe (docs/captures/) avec les données de la base locale
```

- Captures de la 2.4 (boutique, Mon CAP, comptabilité, facture) : faites sur des données simulées, avec les photos des recettes sucrées de la base locale (au-delà, le visuel par défaut) : `ONLY=pc-boutique,telephone-boutique,pc-mon-cap,telephone-mon-cap,pc-comptabilite,pc-facture npm run captures`.
- Captures avec de vraies recettes : celles du site en ligne (pages publiques seulement, rien n'y est écrit, cookies refusés), `BASE_URL=https://les-creations-de-yona.fr RECIPE=<slug> ONLY=telephone-recette,telephone-mode-cuisine npm run captures`. `ONLY` : les captures à refaire (toutes par défaut) ; `RECIPE` : la recette montrée. Les captures 1.5 (recette, ingrédients, mode cuisine, liste de courses, thème sombre) viennent du site en ligne ; la page d'installation, de la pile locale (nouveau bouton).

- Le Chrome installé sur la machine, sans fenêtre (`HEADED=1` pour la voir, `CHROME_CHANNEL=msedge` pour Edge) ; aucun navigateur à télécharger (`playwright-core`). Autre adresse : `BASE_URL`.
- Aucune donnée à préparer : il choisit une recette publiée avec des ingrédients et une étape minutée, et le premier menu publié (sans menu, la partie « Menus » échoue en le disant). La boutique, Mon CAP, les factures, la comptabilité et le brouillon des articles tournent sur des données simulées (`page.route`) : la page est ouverte sans rechargement (`goClient` dans `outils.mjs`), pour que ses données soient demandées par le navigateur et non par le rendu du serveur ; reCAPTCHA est simulé aussi (`fakeRecaptcha`), jusqu'à l'envoi d'une demande. Les minuteurs se vérifient avec une horloge simulée (un quart d'heure en une seconde).
- Couvre : robots et assistants IA (robots.txt, réponse 200 aux robots d'IA, pages en Markdown par `.md` et par `Accept`, `llms-full.txt`, étapes d'installation dans le HTML), accueil, recherche à plusieurs ingrédients, notes, mode cuisine (mise en place, minuteurs, « + 1 min », minuteur libre), minuteurs gardés sur les autres pages et retrouvés après un rechargement, liste de courses par rayon, menus (« Tout ajouter »), bandeau d'installation, Mon CAP (frise, page d'un article, photo en grand, ancienne adresse des observations), « Nouveautés » et rayons du back-office, et les réponses de l'API (400 pour une adresse mal encodée).
- Couvre aussi (2.4) : boutique sur téléphone et ordinateur (catégories, recherche sans accents ni majuscules, « Ma demande » gardée en changeant de page, volet, envoi et page de suivi, demande gardée illisible ignorée, icône de la liste de courses distincte), article de Mon CAP (« 1er », gras, astuce, lien vers le site sans rechargement), facture (génération, feuille, titre du PDF, impression sans menu, commande figée), factures et informations de facturation dans la comptabilité, brouillon d'un article retrouvé après un rechargement (« Reprendre », « Ignorer », onglet caché), motif de la page de connexion.
- Couvre aussi (2.5) : infobulles des icônes de la barre du haut (sous l'icône), premier Tab sur « Aller au contenu », menu téléphone (page en cours sur un voile dans les marges, espace entre pages et sections, croix sans cercle, + qui devient × sur place, section dépliée sans défilement), page Accessibilité (chaque réglage appliqué, gardé sur les autres pages dès l'affichage, rien qui déborde en très grand et espacé, plus de transitions, « Tout remettre par défaut »), déclaration d'accessibilité et liens du pied de page, rien qui déborde à 320 px (accueil, recette, accessibilité, glossaire), « Nouveautés » en Version 2 puis Version 1 et en tableaux à pastilles.
- Accessibilité : chaque page publique (dont Accessibilité et la déclaration), la boutique, un article de Mon CAP et une facture passées à [axe](https://github.com/dequelabs/axe-core) (WCAG 2.1 A et AA, bonnes pratiques), aucun écart toléré ; le détail de chaque problème trouvé est écrit (règle, élément).
- Vitesse et qualité : [Lighthouse](https://developer.chrome.com/docs/lighthouse) sur l'accueil, une recette et un menu, en téléphone simulé (4G lente) ; seuils dans `parcours.mjs` (`LIGHTHOUSE_MIN`) : performance 70, accessibilité 100, bonnes pratiques 95, SEO 100. La performance varie de quelques points d'une mesure à l'autre (78 à 90 en 1.4) : le seuil ne signale que les vraies régressions. Les réponses sont compressées par la passerelle (`encode zstd gzip` dans le Caddyfile), comme Cloudflare le fait en production : sans cela, la mesure locale serait faussée.
- Le back-office sans connexion Google : la réponse « qui est connecté ? » est simulée dans le navigateur (avec la version et le nombre de retours non lus, que le menu du back-office demande), comme les rayons (choisis dans le back-office). Le service worker de l'application est bloqué, sauf sur l'accueil : il relaierait lui-même les appels à l'API, que le parcours ne pourrait plus simuler.

- Écritures admin : en-tête `X-XSRF-TOKEN` recopié du cookie `XSRF-TOKEN`, que `GET /api/admin/me` crée (cette route répond aussi l'adresse, le nom et, si le compte en a une, la photo Google : `picture`). Angular le fait automatiquement. Aucun cookie n'est posé pour un visiteur public.
- Images : le front construit l'URL à partir du `imageId` des recettes et catégories. Réponse `Cache-Control: public, max-age=31536000, immutable` : une nouvelle photo a un nouvel identifiant, donc une nouvelle URL.
- Sauvegarde : à ouvrir comme un lien classique (`<a href="/api/admin/backup">`), pas via `HttpClient`, qui chargerait toute l'archive en mémoire. Restauration : morceaux envoyés par `XMLHttpRequest` (progression), comme les photos (`core/api/image-uploads.ts`).
- Toute route non listée est refusée.
